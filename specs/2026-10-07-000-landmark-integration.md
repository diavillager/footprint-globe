# 랜드마크 소스 연동과 검증

작성: 2026-10-07 (한국 시간)

> 최신 사용자 승인: Geoapify 대신 Wikipedia·Wikidata·Commons로 시험한다. 현재 개발 앱은 Wikimedia만 호출한다. 아래 기존 Geoapify 계약·검증은 이력이며 문서 끝의 Wikimedia 시험 절이 공급자 관련 현행 기준이다.
상태: `codex/landmark-footprints`에서 앱 통합 구현 중. 2026-10-07 사용자가 아래 자동 여행일지 흐름을 요청하고 파일당 횟수 제한 해제를 확정했다. 현재 프로덕션에 제공되는 기능이라는 뜻은 아니다.

## 2026-10-07 자동 여행일지로 변경 확정

사용자 최신 요청은 근접 묶기 자체를 조작하는 기능이 아니라 **JSON 등록 → 원본 경로 → 파일별 동의 → 지역별 장소 조회 → 원본 포인트 대조·장소 중심 묶기 → 사진 조회 → 말풍선과 여행일지로 전체 흐름 탐색**이다. 이전의 묶기 토글·묶음별 조회 버튼 정책을 대체한다.

- 지역을 먼저 조회하고 원본 포인트를 장소와 대조한다. 동일 최근접 장소의 연속 구간 안에서 장소와 가장 가까운 관측을 대표점으로 정해 그 주변 100m 이내를 묶는다. 인접 공백 120분 초과·장소 변경·미연결 기록에서 분리한다. 첫 관측을 무조건 대표점으로 삼던 방식은 폐기하며 원본 관측·목록·분포와 재방문을 보존한다.
- 파일 등록 시 지도 범위를 전체 원본 기록에 맞추고 동의 후 지역 조회·대조가 끝나면 자동으로 묶는다. 조회된 지점에만 가장 가까운 랜드마크 하나를 순번·시간 말풍선으로 표시한다. 클릭하면 후보 목록과 관측 세부정보를 연다. 미조회·빈 결과·실패 지점에는 상시 말풍선을 표시하지 않는다. 왼쪽 목록은 제거하고 파일 등록 때 자동으로 동의 안내를 열고 허용해야 매핑한다. 상단 기록 분포 옆 원형 진행 표시를 가리키거나 누르면 아래에 처리 수·장소/사진 성공·실패·없음·요청 수를 표시한다. 원본 목록은 위치 기록으로 이름을 변경하며 기록 분포 창 상단 좌우 옵션으로 시간 간격·이동 거리를 전환한다. 겹치는 지도 말풍선은 화면 공간에 따라 줄이며 확대·이동하면 다시 선정한다.
- 파일별 안내에서 동의하면 원본 포인트 주변 300m를 덮는 구역의 장소를 자동 조회하고 원본 포인트와 로컬에서 대조한다. 지도 클릭이나 묶음별 조회 버튼은 필요 없다. 동의 전에는 묶지 않은 원본 관측 경로를 표시한다. UTC/KST 오른쪽의 원본 경로/장소별 보기 전환은 원본 관측 전체와 묶음 대표점·랜드마크 표시를 전환하며 동의나 조회 결과를 초기화하지 않는다. 동의 후에도 원본 경로를 유지하며 장소·사진 처리가 모두 끝나야 장소별 보기를 선택할 수 있다. 미허용·처리 중·인증/사용량 오류 중단 시에는 비활성화한다. 완료되어도 자동으로 보기를 전환하지 않는다.
- 검색 조건은 관광 명소·볼거리·박물관, 300m/10개이며 가장 가까운 유효 후보를 ‘추정’으로 표시한다. 이는 실제 방문·체류 확정이 아니다. 상세에서 다른 후보를 선택할 수 있다.
- 사용자가 **‘한도 없이 전체 지점 조회’**를 확정했다. 기존 파일당 32회 제한은 폐기한다. 속도 개선 요청에 따라 동시 최대 3건·250ms 시작 간격으로 변경한다. 요청당 10초 제한·자동 재시도 없음은 유지한다. 같은 검색 구역과 장소 ID의 결과는 공유하되 원본과 재방문 identity는 유지한다. 장소 조회를 먼저 완료하고 고유 대표 장소의 사진을 조회한다. 인증/사용량 오류 시 자동 조회를 중지한다. 그 밖의 실패·빈 결과는 구분하여 표시하고 다음 지점으로 진행한다.
- 후보를 찾으면 Place Details API를 조회한다. `wiki_and_media.image`와 `wikimedia_commons`의 원본·썸네일·File:·Commons 파일 페이지 참조를 해석한다. 파일 참조가 없고 유효한 Wikidata Q ID가 있으면 P18 대표 사진을 조회한다. Commons Imageinfo로 480px 썸네일·저작자·라이선스를 받고 파일 출처와 함께 표시한다. 임의 호스트·SVG·카테고리의 무작위 사진·Wikipedia 이름 검색은 사용하지 않는다. 사진 없음·미지원 참조·조회 실패·브라우저 로딩 실패는 각각 집계한다.
- 이미지 상세 조회도 동시성·타임아웃·취소 제어와 요청 집계에 포함한다. 같은 장소 ID의 상세는 파일 세션에서 한 번만 요청한다. 사진 다운로드는 Wikimedia로 직접 이루어지고 Referrer를 보내지 않는다. 메타데이터 요청은 commons.wikimedia.org와 www.wikidata.org로만 보내며 파일명·Q ID만 전달한다. Geoapify 키·관측 좌표·시각은 전달하지 않는다. CSP는 두 메타데이터 호스트와 upload.wikimedia.org·thumb.wikimedia.org 이미지만 허용한다. 이미지 조회 작업 전체에 10초 제한을 적용하며 하위 메타데이터 요청도 총 요청 수에 포함한다.
- 파일별 동의 안내에 Geoapify 검색 구역 경계 좌표 전송과 Wikimedia 사진 요청을 포함한다. JSON·파일명·시각·기록 ID는 보내지 않는다. 결과·동의·선택은 세션 메모리에만 유지하고 교체·삭제·새로고침 때 초기화한다.
- ‘추가 조회 중단’은 진행 요청을 취소하고 결과를 보존한다. JSON 올리기 옆 ‘지우기’는 기록과 결과를 함께 지운다. 이미 전송한 요청은 회수할 수 없다. 계정 인증·사용량 오류 상태는 파일 세션에서 유지한다.
- 키는 공개 브라우저용 `VITE_GEOAPIFY_API_KEY`를 사용한다. 자동 조회에 파일당 비용 상한은 없으며 계정 할당량은 서비스 설정을 따른다.

## 목적과 근거

Google Timeline의 연속된 근접 관측을 지도 표시용 지점으로 묶고, 주변 랜드마크 후보를 말풍선으로 탐색하게 한다. 여행의 주요 장소를 쉽게 찾되 관측 연결을 실제 이동 경로로, 가까운 명소를 실제 방문으로 오해하지 않게 한다.

- [현행 PRD](../docs/PRD.md), [상세 지도 명세](2026-10-06-005-detailed-map.md)
- [가상 여행 데이터](../docs/travel-demo.md), [비교 프리뷰와 검증 기록](../tools/landmark-preview/README.md)
- 사용자 확정: 입력 소스는 Google Timeline, 연속 근접 관측 묶기와 랜드마크 말풍선 개발, 랜드마크 API는 Geoapify.
- 지도 표시는 기존 MapLibre GL JS + MapTiler를 유지한다. 삼성 자료, 사용자 사진 첨부, 로그인, DB, 영구 저장, 실제 경로 예측은 이번 범위가 아니다.
- 사용자가 명소 이름을 나중에 알려줄 수 있으므로 합성 여행의 현재 좌표를 확정 랜드마크의 정확한 위치로 취급하지 않는다.

## 범위와 흐름

Timeline 선택 → 로컬 파싱·시간순 정렬·원본 지도 → 파일별 동의 → 구역별 장소 조회 → 원본 포인트 대조·장소 중심 묶기 → 연결된 고유 장소 사진 조회 → 가장 가까운 랜드마크의 사진 또는 텍스트 말풍선 → 클릭하여 후보·세부정보 탐색.

원본 관측·시각·순서는 보존한다. 개별 관측은 원본 목록에서 계속 탐색한다. 연결선은 묶기 전후 동일한 시간 흐름을 표현하며 이번 기능 때문에 공백 연결을 임의로 끊거나 실제 도로에 맞춰 경로를 추정하지 않는다. 원본 기반 목록·분포의 계산은 표시 묶음 수로 대체하지 않는다.

현재 앱 지원 입력인 rawSignals 위치 관측을 사용한다. semanticSegments·timelineObjects 지원 확대, 내보내기 형식 변경은 포함하지 않는다. 기존 크기·건수 한도를 유지한다.

## 관측 묶기

- 시간순으로 인접한 관측만 한 묶음으로 처리한다. 다른 곳을 거쳐 같은 장소에 돌아오면 별도 묶음이다.
- 한 점씩 가까운 것만 확인해 이동 구간 전체가 연쇄적으로 한 묶음이 되지 않도록 기준점 또는 묶음 범위를 제한한다.
- 묶음에는 원본 관측 ID 목록, 시작·종료 시각, 대표 좌표, 관측 수를 유지한다. 대표 좌표 변경·필터·지도 확대가 원본 기록이나 사용자 연결의 identity를 바꾸지 않도록 한다.
- 묶음 시간 범위는 관측 시작과 끝이며, 그 사이 내내 머물렀다는 확정 체류 시간이 아니다.
- 같은 지점이라도 인접 관측 공백이 120분을 넘으면 별도 묶음이다. 묶음을 분리하는 기준과 지도 연결선을 끊는 기준은 별개이며 긴 공백의 연결선은 유지한다.
- 비교 프리뷰의 100m·120분은 최초 실험값이었으며 이후 위 사용자 답변으로 이번 구현의 기본값으로 확정됐다.

## 데이터 계약과 모듈 경계

기존 파서·정규화 모델과 분리된 표시 계층으로 구현한다. 다음은 구현 계약의 초안이며 기존 ID 규칙과 맞춰 구체화한다.

| 객체 | 유지할 정보 | 의미 |
|---|---|---|
| ObservationGroup | groupId, sourceObservationIds, representativeCoordinate, startInstant, endInstant, observationCount | 화면에서 묶은 관측, 방문 확정 아님 |
| LandmarkCandidate | provider=geoapify, providerPlaceId, name, coordinate, categories, distanceMeters, attribution | API가 반환한 주변 후보 |
| LandmarkQueryState | groupId, requestGeneration, status, candidates, fetchedAt, fixedErrorCode | 미조회·조회 중·성공·빈 결과·실패 구별 |
| LandmarkAssociation | groupId, candidateId, confirmationState | 후보 표시와 사용자 선택을 구별하는 확장 연결 |

묶기 함수는 지도 라이브러리를 참조하지 않는다. Geoapify 어댑터는 요청 생성·응답 검증을 담당하고 화면은 정규화된 후보만 받는다. 원본 ID 목록과 위치 전체 경로는 API 요청 객체에 포함하지 않는다. 후보 이름은 HTML로 실행하지 않고 일반 텍스트로 표시한다.

## Geoapify 검색과 말풍선

- Places API의 사각형 지역 검색으로 tourism.attraction / tourism.sights / entertainment.museum 범주를 수집한다. 300m 반경·최대 10개·거리 근접 순 정렬은 수집 후 원본 포인트별 로컬 대조에 적용한다.
- 좌표 유효 범위·순서와 유효한 0 좌표를 검사한다. 비정상 응답·좌표·이름 누락은 안전하게 제외한다. `-` 등 의미 없는 이름은 확정 명소명처럼 제시하지 않는 표시 정책이 필요하다.
- 가까운 순서가 유명도나 방문 확률 순서는 아니다. 카테고리와 거리를 함께 보여주고 자동 방문 확정은 하지 않는다.
- 지도 말풍선 왼쪽에는 잘리지 않는 사진, 오른쪽에는 번호·최근접 장소명·N년 N월 N일 약 HH:mm:ss (UTC/KST)를 표시한다. 클릭하면 중앙 상세창에서 큰 사진·출처/저작자/라이선스·묶인 관측 수·시간 범위·후보 명칭/거리/종류/출처를 표시한다. 후보가 없으면 원래 위치 점만 유지한다.
- 사용자는 후보 버튼을 눌러 선택하거나 해제할 수 있다. 후보 선택은 해당 파일 세션의 화면 상태이며 사진의 방문 지정 기능과 별도다.
- 지도 이동·회전·확대 중 점·선·말풍선의 좌표계를 통일한다. 말풍선이 화면 밖으로 사라지거나 가까운 점을 가려 선택을 방해하지 않도록 한다.

## 개인정보·요청·오류

Geoapify 채택 결정은 실제 사용자 위치의 무조건적인 외부 전송 승인이 아니다. 위 최신 정책에 따라 파일별 동의를 거쳐 전체 지점을 자동 조회한다. 에이전트 검증에는 합성 자료만 사용하며 실제 파일은 사용자가 직접 선택한다.

- 전체 JSON, 날짜·시각, 기록 식별자, 파일명은 외부 검색에 보내지 않는다. 필요한 검색 구역 경계 좌표와 검색 조건만 요청에 사용한다.
- 브라우저 직접 요청을 사용한다. 브라우저 키는 비밀이 아니며 origin 제한이 필요하다. 별도 서버 프록시는 추가하지 않는다. 브라우저 개발자 도구에는 요청 좌표·공개 키가 보일 수 있지만 앱은 요청 URL·응답 원문을 로그로 출력하지 않는다.
- 키·원본 값·요청 URL·API 오류 원문을 Git, 콘솔, 분석 도구에 남기지 않는다. 오류는 고정 코드로 표현한다.
- 요청은 제한된 동시성·중복 제거·중단 기능을 제공한다. 지도 이동이나 재렌더마다 전체 묶음을 자동 조회하지 않는다. 401/403은 설정 오류, 429는 사용량 제한, 타임아웃·네트워크 실패는 재시도 가능한 실패로 구별하고 자동 무한 재시도하지 않는다.
- 파일 교체·기록 삭제·컴포넌트 종료 후 이전 요청 결과가 새 기록에 붙지 않도록 취소와 세대 구분을 사용한다. 묶기 기준 변경도 캐시 키와 요청 세대에 반영한다.
- 캐시는 해당 파일 세션의 메모리에만 유지하고 파일 제거 시 원본과 연결된 참조를 해제한다. 디스크·DB 저장은 추가하지 않는다. [공식 Places 안내](https://www.geoapify.com/places-api/)에서 캐시 허용과 Geoapify·OpenStreetMap 출처 표시 요구를 2026-10-07 확인했으며 UI에 출처 링크를 표시한다. 계정별 적용 약관·할당량은 실제 사용 전에 별도로 확인한다.
- API 실패와 빈 검색 결과를 구별한다. 어느 경우에도 위치 표시·기존 연결선·파일 탐색을 사용할 수 있어야 한다.
- 서비스별 최신 요금·할당량은 배포 전에 계정에서 확인한다. 과거 프리뷰의 32회 제한은 폐기했으며 무료 사용을 보장하지 않는다.

## 2026-10-07 실제 브라우저 연결 후속 검증

- Geoapify [Place Details 공식 문서](https://apidocs.geoapify.com/docs/place-details/)에서 `id`, `features=details`와 `wiki_and_media.image`를 확인했다. 모든 장소의 사진 제공을 보장하지 않는다.
- 자동 여행일지·사진·32회 초과 조회·오류 중단·파일 교체·모바일 배치는 합성 데이터와 모의 API로 검증했다. `npm run check`(153개 테스트·타입 검사·빌드)와 개발/프로덕션 Edge smoke를 통과했다. 기존 MapLibre 대형 번들 경고는 남아 있다. 이 변경의 실제 이미지 제공률과 사용자 기록에서의 유용성은 사용자 로컬 확인이 남아 있다.
- 이전 수동 조회 검증 기록은 당시 구현 이력이며 현재 자동 흐름의 실제 서비스 검증을 대신하지 않는다.

- 후속 화면 정리: 위치 기록 명칭, 통합 분포의 좌우 기준 전환, 장소 매핑 창을 닫은 뒤 조회 지속, 미조회/빈 결과/실패 말풍선 제외, 대표 말풍선 클릭과 후보 선택 후 최근접 대표 유지도 합성 Edge smoke로 검증한다.

## 사진 처리 보강

- 사진 집계는 중복을 제외한 대표 장소 ID 기준으로 조회 중·표시 대기·표시 확인·없음·미지원·조회 실패·브라우저 로딩 실패·취소를 구분한다. 지도 밖 사진의 표시 대기는 실패가 아니다. 장소 검색도 일치·빈 결과·실패를 구분한다.
- 총 요청 수에는 Geoapify와 Wikidata/Commons 메타데이터 요청을 포함하며 Wikimedia 메타데이터 횟수를 별도로 표시한다. 브라우저 이미지 파일 다운로드 횟수는 이 API 요청 집계에 포함하지 않는다.
- 사용자의 기존 549개 지점 결과는 재검증하지 않았다. 공개 예제 파일과 공개 명소 Q243으로 실제 Wikidata P18→Commons Imageinfo의 이미지 주소·저작자·라이선스 반환을 확인했다. 실제 사진 화면 검증은 합성 이미지 응답으로 수행한다.
- Commons의 thumb.wikimedia.org 주소, 파일명 공백/밑줄 동치와 썸네일 참조를 지원한다. 임의 이미지 호스트는 계속 제외한다. 이미지가 없으면 다른 후보의 사진을 대표 장소의 사진처럼 붙이지 않는다.
- 근거: [MediaWiki Imageinfo](https://www.mediawiki.org/wiki/API:Imageinfo), [Wikibase API](https://www.mediawiki.org/wiki/Wikibase/API).

- 보강 검증: `npm run check`의 158개 테스트·타입 검사·빌드 통과. 개발/프로덕션 Edge smoke에서 Wikidata→Commons 참조 해석, 사진 렌더링, 로딩 실패 집계, 파일 교체·취소와 기존 앱 회귀 검증을 통과했다. 기존 MapLibre 대형 번들 경고는 유지된다.

## 사진 표시 대기 접근 보완

- 사진이 준비된 지점이 사진 없는 앞 지점과 같은 화면 셀에 있을 때 뒤 지점의 말풍선이 제외되던 문제를 보완한다. 같은 셀과 겹침 정리에서 사진이 있는 지점을 우선하며, 각 지점의 대표 랜드마크는 여전히 가장 가까운 후보로 유지한다.
- 장소 매핑에 ‘사진 있는 장소 보기’ 버튼을 제공한다. 사진을 찾은 서로 다른 대표 장소를 차례로 선택하고 지도를 이동하며, 상세 말풍선에 사진을 즉시 로드한다. 이미 받은 장소·사진 메타데이터를 재사용한다.
- ‘표시 확인’ 집계는 실제 화면 가시성을 보장하지 않으므로 ‘불러오기 성공’으로 명확히 한다. 지도 밖·겹침 처리·지연 로딩 때문에 사진 주소를 확보해도 표시 대기로 남을 수 있다.
- 사용자의 516개 기록 원본을 열람하지 않고 같은 좌표 재방문 합성 자료로 사진 없는 앞 지점과 사진 있는 뒤 지점의 표시 우선순위 및 상세 사진 접근을 검증한다.


## 등록 안내·경로 전환·조회 속도 보완 (2026-10-07)

- 현재 요청 흐름은 로컬 파싱 → 파일별 동의 안내 → 허용 시 전체 장소/사진 매핑이다. 거절·닫기는 외부 장소 요청을 시작하지 않는다.
- 동시 3건, 250ms 시작 간격은 Geoapify 공개 Free 요금제의 초당 5건 이내에서 응답 대기를 병행하기 위한 구현이다. 계정별 할당량은 별도이며 429에서 추가 조회를 중단한다. 근거: [Geoapify 요금제](https://www.geoapify.com/pricing/).
- 현재 진행률은 지역 조회 65%, 원본 포인트 대조 15%, 고유 대표 장소의 사진 처리 20%로 계산한다. 포화 구역의 추가 페이지·분할은 해당 원래 구역이 끝나야 완료로 집계한다. 사진 성공은 주소 확보이며 실제 사진 로딩 오류는 실패로 반영한다. 빈 결과와 사진 없음은 오류와 구분한다.
- 합성 지연 테스트에서 1초 조회 6건을 3초 이내에 처리하고 최대 동시 3건·최소 시작 간격 250ms, 정확히 동일 좌표의 별도 재방문 결과 공유, 전 요청 취소와 늦은 응답 차단을 검증한다. 이는 실제 네트워크의 속도 보장이 아니다.

- 보완 검증 결과: `npm run check` 통과(자동 테스트 160개·타입 검사·빌드). 개발/프로덕션 Edge 합성 smoke에서 등록 시 안내, 동의 전 요청 0건, 경로 전환, 중앙 상세창, 사진 contain 표시, 모바일 진행 표시 아래 말풍선, 오류·취소·파일 교체를 확인했다. 실제 사용자 파일의 속도와 사진 공급률은 사용자의 로컬 확인이 남아 있다. MapLibre 번들 크기 경고는 기존과 같이 남는다.

- 경로 보기 전환에서는 중심·확대 수준·회전·기울기를 유지한다. 전체 범위 맞춤은 새 파일 등록 또는 지도 재생성 때만 수행한다. 진행 원 안의 수치는 % 기호 없이 숫자만 표시하고 선 두께는 6px로 표시한다.
- 진행 원은 인라인 기준선 여백 없이 툴바 행의 수직 중앙에 배치하여 위아래 간격을 동일하게 유지한다.


## 장소 분류·상세창 및 사진 공급 보완 조사

- 진행 숫자는 13px·700 굵기이며 UTC/KST 활성 텍스트와 같은 #126456을 사용한다.
- Geoapify 공식 분류 계층을 로컬 한국어 사전으로 표시한다. 가장 구체적인 알려진 분류를 우선하고 상위 중복을 제거한다. 예: tourism → tourism.sights → tourism.sights.memorial은 ‘기념물’ 하나로 표시한다. 알려지지 않은 하위 분류는 알려진 상위로, 전혀 모르는 값은 ‘장소’로 표시한다. 원본 응답의 분류는 보존하며 외부 번역 API를 사용하지 않는다. [공식 분류](https://apidocs.geoapify.com/docs/places/)
- 지도 말풍선의 ‘추정 장소’ 문구 대신 분류를 표시한다. 실제 방문을 확정하지 않는다는 설명은 상세창과 동의 안내에서 유지한다.
- 상세창은 왼쪽 세로 후보 목록·오른쪽 선택 장소의 이름, 분류, 사진, 거리, 좌표로 구성한다. 최초에는 최근접 후보가 선택되며 다른 후보 선택이 지도 대표 장소를 바꾸지 않는다. 상세창의 철회·결과 삭제 버튼과 요청 집계는 제거한다. 아직 사진을 조회하지 않은 후보는 미조회 상태를 표시하며 대표 장소의 사진을 대신 사용하지 않는다.

사진 조사 결과(새 제공자 연동은 미구현):

1. 현재 구현은 Geoapify 상세의 image/wikimedia_commons 및 Wikidata P18에서 파일을 찾는다. 따라서 ‘없음’은 해당 참조에서 사진을 찾지 못했다는 뜻이며 인터넷 전체에 사진이 없다는 뜻이 아니다. 전체 후보가 아니라 각 지점의 최근접 대표 장소만 자동으로 사진을 조회한다. [Geoapify 상세](https://apidocs.geoapify.com/docs/places/place-details/)
2. 우선 보완 후보는 연결된 Wikipedia 문서의 PageImages API이다. 문서 제목으로 대표 이미지·썸네일을 조회하고 pilicense=free를 적용할 수 있다. Commons의 저작자·라이선스를 계속 확인해야 하며, 새로운 Wikipedia 요청 대상·동의 안내·CSP 변경을 검토해야 한다. 아직 실제 자료의 사진 공급률 개선은 측정하지 않았다. [PageImages](https://www.mediawiki.org/wiki/Extension:PageImages)
3. 연결된 문서가 없으면 장소명·좌표 기반 문서 검색을 고려할 수 있지만 같은 이름이나 주변 다른 장소를 자동으로 같은 장소로 취급하면 안 된다. 이름·거리·분류 일치 검증이 필요하고 좌표의 추가 전송 결정이 필요하다. [Geosearch](https://www.mediawiki.org/wiki/API:Geosearch)
4. Google Places Photos는 검색/상세에서 받은 사진 리소스로 이미지를 조회할 수 있고 저작자 표시가 필요하다. Google 장소 ID 매칭과 키·과금 설정이 필요하다. Google 정책은 지도 위 Places 결과를 Google 지도에 표시하도록 요구하므로 현 MapTiler 말풍선에 바로 추가하는 방식으로 진행하지 않는다. [사진 API](https://developers.google.com/maps/documentation/places/web-service/place-photos), [표시 정책](https://developers.google.com/maps/documentation/places/web-service/policies)


## 포인트 정보·사진 탐색·중단과 일본 샘플 보완

- 일반 포인트(원본 경로 및 장소별 보기의 미매핑 포인트)는 지도 말풍선으로 표시한다. 장소별 보기에서 최근접 후보가 매핑된 포인트만 중앙 장소 상세창을 연다.
- 사진 순환 버튼은 상세창 닫기 시 선택 ID가 초기화되어 첫 장소로 돌아가던 구조였다. 사진이 있는 고유 장소 전체를 이름 목록으로 제시하고 직접 선택한다. 이미지 로딩 실패는 탐색 목록에서 제외한다.
- ‘추가 조회 중단’은 스케줄러와 진행 중 요청을 멈추되 완료 결과를 보존한다. 새 요청은 시작하지 않는다. 삭제는 JSON 올리기 옆 지우기로 통합한다. 미완료·중단된 파일은 기존 완료 전 전환 금지 정책을 유지한다.
- 스크루 전시물은 현장 취재 사진상 가모메 광장에 있는 전시물이다. [현장 기사](https://fukuoka-leapup.jp/city/202512.68562). 원본 OSM 좌표를 직접 대조하려던 Overpass 요청은 실패했으므로 Geoapify 좌표의 정밀 정확도까지 검증한 것은 아니다.
- 앱의 말풍선 기준은 장소 좌표가 아닌 관측 대표점이다. 일본 가상 입력은 직선 보간이며 항구를 지나는 가상 관측이 생길 수 있었다. 후쿠오카 북쪽 거점을 내륙으로 바꾸고 새 파일로 제공한다. 데이터 공급자 교체로 잘못된 입력 좌표가 고쳐지는 것은 아니다.
- 공급자 대안: Google Places는 사진 리소스를 제공하지만 지도 표시 정책상 Google 지도 전환을 함께 검토해야 한다. Foursquare도 장소 사진 API를 제공하므로 MapTiler를 유지하는 대안 후보이며 계약·지역별 공급률 확인이 필요하다. 공식 API 존재만으로 Geoapify보다 정확하거나 일본 사진이 풍부하다고 판단하지 않는다. [Google 사진](https://developers.google.com/maps/documentation/places/web-service/place-photos), [Google 정책](https://developers.google.com/maps/documentation/places/web-service/policies), [Foursquare 사진](https://docs.foursquare.com/fsq-developers-places/reference/place-photos).
- 공급자 선택 전 합성 경로가 아닌 공개된 실제 장소의 정답 좌표·명칭으로 동일 지역의 위치 오차, 이름 일치, 사진 보유율을 비교하는 것이 적절하다. 이번에 새 서비스 키·유료 요청·외부 전송 또는 지도 공급자 변경은 추가하지 않았다.


## 지역 선조회와 장소 중심 묶기 (2026-10-07)

사용자는 여행 지역을 먼저 수집한 후 포인트와 대조하는 방식을 승인했다. 이번에는 Geoapify를 유지하고, 실제 확인 후에도 정보 불확실성이 남으면 공급자 교체를 검토한다.

- 전체 여행을 하나의 거대 사각형으로 감싸지 않는다. 원본 포인트의 300m 주변을 덮는 위도 0.02도(약 2.2km) 격자를 사용하고 경도 폭은 위도에 따라 보정한다. 날짜변경선·극점도 처리하며 포인트가 없는 장거리 이동 사이 구역은 조회하지 않는다.
- GET `/v2/places`에 `filter=rect:west,south,east,north`, `limit=500`, `offset`, 기존 범주·`lang=ko`·브라우저 키만 보낸다. JSON·시각·기록 ID·파일명은 보내지 않는다. 동의 전 지역 계산은 로컬에서만 수행한다.
- 한 구역의 두 페이지가 모두 500개이면 4개 하위 구역으로 나누고 최대 3단계까지 반복한다. 최종 포화는 `SEARCH_INCOMPLETE`로 표시한다. 유효하지 않은 응답 항목을 제외하기 전 원시 건수로 포화를 판단한다. 페이지·구역 중복은 장소 ID로 제거한다.
- 각 원본 포인트 주변 구역 중 하나라도 실패·미완료이면 해당 포인트를 조회 실패로 구분한다. 정상 조회한 구역에 후보가 없는 경우만 후보 없음으로 집계한다. API 결과 자체의 누락까지 검출하거나 완전 수집을 보장하지는 않는다.
- 로컬에서 각 원본 포인트와 후보 좌표의 지표면 거리를 계산하여 300m 안 최대 10개를 정렬한다. 최근접 장소가 같은 연속 구간을 찾고 그 장소와 가장 가까운 관측부터 대표점으로 선택해 양옆의 연속된 100m 이내 관측을 묶는다. 남은 구간에도 같은 과정을 적용한다. 거리가 같으면 원본 시간순서를 따른다. 100m를 넘는 이동을 연쇄적으로 합치지 않는다.
- 미연결·실패 포인트는 원본 단일 지점으로 남긴다. 묶음 순서는 최초 구성원 시각 기준이며 대표점·말풍선 시각은 장소와 가장 가까운 실제 관측이다. 연결선은 이 대표 관측 사이의 흐름이고 방문 확정·도로 복원이 아니다.
- 모든 지역 조회와 원본 대조가 끝난 뒤 연결된 고유 대표 장소의 사진만 조회한다. 사진 공급원을 추가하지 않으므로 사진 보유율 자체의 개선은 보장하지 않는다.
- 진행 안내는 지역 조회/실패, 포인트 대조, 장소 연결/실패/후보 없음, 수집 장소·묶음 수, 사진 상태와 요청 수를 구분한다. 파일 교체·지우기는 요청을 취소하고 지역·장소·사진 캐시를 함께 해제한다.
- [Geoapify 지역 수집 안내](https://apidocs.geoapify.com/how-to/place-discovery/retrieve-places-large-area/)는 넓은 영역의 완전 추출을 보장하지 않으며 작은 영역 분할과 장소 ID 중복 제거를 권장한다. [페이지 조회](https://apidocs.geoapify.com/how-to/place-discovery/paginate-place-results/)와 [Places API](https://apidocs.geoapify.com/docs/places/)를 따른다.

## Wikipedia·Wikidata·Commons 시험 (2026-10-07)

- 사용자 요청에 따라 현재 브랜치의 장소 소스를 교체해 검증한다. 현재 UI에서 Geoapify 요청 또는 fallback을 하지 않으며 CSP에서도 Geoapify를 제거한다. 이전 어댑터·테스트는 비교 이력으로 유지한다. API 키 없이 이용하고 MapTiler 지도는 유지한다. 배포·병합 승인을 뜻하지 않는다.
- 파일별 동의 화면에서 새 요청 대상을 안내한다. Wikipedia의 일본어·영어 사이트에 구역 경계만, Wikidata에 Q ID, Commons에 파일명만 전송한다. 원본 JSON·시각·파일명·기록 ID는 전송하지 않으며 credentials omit·no-referrer·redirect error를 적용한다.
- `generator=geosearch`와 bbox로 언어별 최대 500개 문서의 primary 좌표·좌표 유형·Wikidata ID·자유 이용 대표 이미지 파일명을 받는다. `colimit/pilimit=max`로 속성 수 제한을 완화하고 속성 continuation을 문서 ID별 병합한다. 반복·16페이지 초과 continuation은 SEARCH_INCOMPLETE다. 500개 포화는 구역 4분할(최대 3단계)로 처리하며 임의 offset을 사용하지 않는다.
- 동일 Wikidata ID는 하나로 합치고 일본어 이름·좌표를 우선한다. Q ID가 없으면 언어와 문서 ID로 식별한다. 좌표가 범위 밖이거나 city/country/state/adm1st/adm2nd/event 유형이면 제외한다. 지리 좌표가 있는 일반 시설은 포함될 수 있으며 기존 관광 범주와 동등한 검색이라고 주장하지 않는다. 언어별 좌표 문서의 누락과 사진 없음도 정상적으로 발생할 수 있다.
- 300m 내 최근접 후보 최대 10개와 장소 중심 100m·120분 묶기, 원본 경로 기본 표시·완료 후 수동 전환은 유지한다. 후보 분류는 Wikipedia 좌표 유형에 따른 제한된 한국어 분류이며 unknown은 ‘위키백과 장소’다. 상세에서 선택한 장소 원문 링크를 제공한다.
- 대표 장소의 Wikidata P18(선호 rank 우선·deprecated 제외)을 먼저 확인한다. 없거나 Commons에 해당 파일이 없으면 같은 문서의 `pilicense=free` 대표 파일을 시도한다. 임의 이름 검색·주변 다른 장소 사진은 사용하지 않는다. Commons Imageinfo의 480px 썸네일·Artist·LicenseShortName을 검증하며 라이선스가 누락되면 실패로 구분한다. 기존 Commons 이미지 호스트·래스터 형식 제한을 유지한다.
- 모든 메타데이터 호출을 400ms 이상 간격으로 제한한다(분당 약 150회). 최대 동시 3개 작업·작업 전체 10초 제한. HTTP 429/503·ratelimited/maxlag에서 새 작업을 중단하고 자동 재시도하지 않는다. 403도 서비스 접근 오류로 중단한다. 총 요청 수는 예약 작업 수가 아닌 실제 fetch 시작 건수이며 지역/사진을 별도로 집계한다.
- 지역·문서·사진 캐시는 파일 세션별 메모리만 사용한다. 지우기·교체·dispose 때 모두 해제하고 abort 이후 늦은 응답을 반영하지 않는다. 캐시 영구 저장과 실제 사용자 파일 열람은 추가하지 않는다.
- 근거: [Geosearch](https://www.mediawiki.org/wiki/API:Geosearch), [GeoData](https://www.mediawiki.org/wiki/Extension:GeoData), [PageImages](https://www.mediawiki.org/wiki/Extension:PageImages), [Wikimedia 속도 제한](https://www.mediawiki.org/wiki/Wikimedia_APIs/Rate_limits), [Commons 재사용](https://commons.wikimedia.org/wiki/Commons:Reusing_content_outside_Wikimedia).

공개 일본 명소 실제 API 점검: 구마모토성·오호리 공원·후쿠오카성 3곳 모두 정확한 문서명 일치와 사진 메타데이터·라이선스를 확보했다. 각각 5·4·4회 메타데이터 요청을 사용했다. 독립적인 좌표 정밀도 검증이나 모든 명소의 사진 보유율을 입증하는 표본은 아니다. 실제 사용자 자료와 Geoapify는 사용하지 않았다.


Wikimedia 실제 검증 결과(2026-10-07, 완전 합성 일본 여행): 원본 관측 2,446개, 검색 구역 87/87개 완료·실패 0, 수집 장소 768곳, 주변 후보 연결 2,297개 관측·후보 없음 149개·오류 0개, 장소 중심 묶음 529개. 연결된 고유 대표 장소 98곳 중 86곳의 사진 주소·라이선스를 확보했고 12곳은 사진 없음이었다. 요청은 363회(지역 검색 179회, 사진 메타데이터 184회), 경과 시간 146초였다. 이 실행은 Node에서 메타데이터를 확인한 것이므로 86장 전체의 이미지 다운로드·표시를 검증한 수치는 아니다. 주변 후보 연결은 실제 방문이나 위치 정확성을 입증하지 않는다.

별도 Edge 실제 연결 검증에서는 공개 구마모토성 좌표 하나에 가상 시각을 붙여 JSON 등록 → 동의 → 원본 기본 유지 → 장소별 보기 → 말풍선 및 상세창의 실제 Commons 사진 로딩을 확인했다. Wikipedia·Wikidata·Commons 메타데이터 5회, 사진 파일 1회, Geoapify 0회였다. 사진의 저작자·CC BY-SA 3.0·원문 링크를 확인했으며 지도 요청만 모의 처리했다. `tests/wikimedia-live-smoke.cjs --live`로 재현한다. 전체 여행 검증은 `tools/check-wikimedia.mjs --live`이며 사용자 원본은 읽지 않았다.


최종 로컬 검증: `npm run check`의 타입 검사·자동 테스트 194개(샘플 66개, 앱 128개)·빌드 통과. `tests/app-smoke.cjs`와 `tests/landmark-smoke.cjs`는 개발·프로덕션 빌드에서 통과했다. API 키 없이 파일별 동의, 네 합성 여행, 사진·지역 재사용, 오류·취소, 모바일, 카메라 유지 및 사진 목록을 확인했다. 실제 Edge 시험에서는 브라우저 fetch의 실행 컨텍스트 오류를 발견해 기본 fetch를 globalThis에 바인딩했고 실제 사진 표시까지 재검증했다. 기존 MapLibre 500 kB 초과 청크 경고는 남는다. 사용자 실제 기록 검증·운영 배포·소스 최종 채택은 이번 결과와 구별한다.


### 한국어 장소 이름 표시 (2026-10-07)

사용자 요청에 따라 말풍선·사진 목록·상세 후보 목록·상세 제목의 장소 이름을 한국어 우선으로 바꾼다. 기존 일본어·영어 지역 조회에 `pageterms`(`wbptlanguage=ko`, `wbptterms=label`)와 `langlinks`(`lllang=ko`)를 함께 요청한다. 한국어 Wikidata 이름 → 한국어 문서 제목 → 원문 제목 순으로 표시하며, 한국어가 없는 장소는 원문을 보존한다. 언어 fallback의 외국어 이름을 한국어로 오인하지 않고 한글 포함 여부를 확인한다. 외부 번역 서비스와 별도 장소별 이름 조회는 추가하지 않는다. 추가 속성 continuation이 발생하면 기존 속성과 함께 병합하며 실제 요청 수에 포함한다. 같은 Wikidata ID의 다른 언어 문서에서 한국어 이름을 보완할 수 있다. 이름이 바뀐 장소의 현지 이름은 상세 화면에 병기한다. 기존 장소 ID·좌표·출처·사진 연결·묶음은 그대로 유지한다.

실제 공개 API에서 熊本城 → 구마모토성, 大濠公園 → 오호리 공원, 福岡城 → 후쿠오카성을 확인했다. Edge의 공개 구마모토성 합성 1지점 검증에서 말풍선·상세 제목의 한국어, 상세의 현지 이름, 실제 사진 표시가 통과했으며 메타데이터 5회·사진 1회·Geoapify 0회였다. 타입 검사·자동 테스트 196개·빌드가 통과했고, 기존 MapLibre 청크 크기 경고는 유지된다.

한국어 표시 변경 후 개발·프로덕션 `tests/landmark-smoke.cjs`도 통과했다. 모의 API는 외국어 원문과 한국어 이름을 함께 제공하며 말풍선·후보 선택·사진 목록·모바일을 검증한다. 현재 제공 중인 `http://127.0.0.1:4175/`에서도 공개 구마모토성 1지점으로 한국어 이름과 현지 이름·실제 사진 표시를 확인했다.


### 장소 번호 띠와 선택 해제 (2026-10-07)

사용자는 직전 확대 단계별 숫자 마커·이름표 변경(`281ab3a`)을 되돌리고 방위 눈금과 같은 가로 장소 탐색 UI를 요청했다. 해당 변경을 되돌려 기존 지도 말풍선을 복원하고, 화면 하단 중앙에 장소 번호 띠를 추가한다. 후속 사용자 지시에 따라 배경 패널·제목·화살표·스크롤바·번호 위의 별도 눈금을 없애고 번호 중심을 하나의 가로선으로 잇는다.

- 매핑된 대표 지점만 기존 시간순으로 나열하며 번호는 1부터 연속 부여한다. 미연결·실패 원본 관측은 제외하고 같은 장소 재방문은 별도 기록으로 유지한다. 번호 띠·지도 말풍선·상세 제목은 같은 번호를 사용한다.
