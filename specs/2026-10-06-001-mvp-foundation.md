# MVP 병렬 개발 공통 기반

상태: 사용자가 공통 준비 진행과 이 spec 작성을 승인했다. 이 문서는 앱 기능 완료를 의미하지 않는다.

## 목적과 관련 요구사항

[PRD](../docs/PRD.md)의 로컬 파일 처리·지구본 탐색·사진 연결 흐름을 데이터 처리와 화면 작업으로 나누기 위한 기반이다. 사용자는 사진을 붙일 방문을 직접 지정하기로 결정했다. 위치 점 연결부터 개발할지와 연결 정책은 이후 결정한다.

## 이번 범위

- React·TypeScript·Vite 앱 실행, 타입 검사, 합성 테스트, 배포용 빌드 환경
- React나 지구본 라이브러리에 의존하지 않는 공통 자료형
- 화면 담당이 실제 파서 없이 사용할 완전 합성 데이터와 비동기 대체 함수
- PRD 결정 반영, 파일 담당 범위와 병합·검증 순서

실제 JSON 파서, 지구본 표시, 사진 첨부, 방문 지정 UI, 경로 연결 알고리즘과 worktree 생성은 이번 구현에서 제외한다. 기존 샘플 생성기의 지원·치환·제외 정책은 변경하지 않는다.

## 공통 계약

코드 기준은 [timeline.ts](../src/domain/timeline.ts)다.

| 자료형 | 의미와 소유권 |
| --- | --- |
| TimelineData | 데이터셋 ID, 위치 관측, 원본 방문, 원본 경로. 데이터 담당이 반환하고 화면은 읽기 전용으로 소비 |
| Observation | 별도 ID, 십진수 위도·경도, 원본 시각 표현 및 비교용 epoch 밀리초 |
| RecordedVisit / RecordedPath | 원본이 명시한 기록. 추정 연결이나 사용자가 지정한 방문과 혼합하지 않음 |
| ManualVisit | 사용자가 관측점을 선택해 지정한 방문. 방문 ID·데이터셋 ID·관측점 ID로 연결 |
| PhotoAttachment | 방문 ID·데이터셋 ID와 세션 내 Object URL. 화면 담당이 생성·해제 책임 |
| ParseResult | 성공 여부에 따른 결과와 고정 코드·집계 건수. 원본 값·필드명·파일명·예외 메시지를 진단에 넣지 않음 |

파서 경계는 `(text, datasetId) => Promise<ParseResult>`다. 비동기 형식은 이후 worker 사용을 가능하게 할 뿐, 이번에 worker를 구현하거나 필수로 정하지 않는다. 파일 선택과 읽기는 화면 측, JSON 판별·검증·정규화는 데이터 측의 책임이다. 입력 자체를 콘솔·서버에 전달하지 않는다.

관측 시각의 원본 표현은 정밀도·시간대 확인을 위해 메모리에 유지하며 화면 표시 시간대는 후속 결정이다. `epochMs`만으로 밀리초 미만의 순서를 확정하지 않는다. ID는 데이터셋 안에서 고유하고 필터·정렬·표시 단순화 중 유지한다. 새 파일 선택은 새 데이터셋이며 파일 간 ID 복원이나 사진 영구 보존은 제공하지 않는다.

관측점 ID는 방문 ID와 다르다. 같은 좌표의 다른 시각 기록을 합치지 않는다. 사용자 지정 방문에 임의의 체류 기간을 넣지 않는다. 사진의 URL은 데이터셋 교체·사진 제거·컴포넌트 종료 시 해제해야 한다. 해당 동작은 화면 구현 단계에서 검증한다.

## 합성 데이터

[합성 fixture](../src/fixtures/timeline.ts)는 사용자 파일이나 생성 샘플을 복사하지 않고 작성한다. 0 좌표, 다른 위치, 같은 좌표로의 재방문, 긴 시간 공백을 포함한다. 경로·원본 방문 배열은 비어 있으며 자동 연결하지 않는다. 수동 방문 예제는 같은 좌표의 두 관측에 서로 다른 ID를 연결한다.

`syntheticParser`는 입력을 해석하지 않는 화면 개발용 대체 함수다. 실제 파일 선택에 연결하지 않는다. 원본 형식별 parser fixture는 데이터 담당이 기존 완전 합성 입력을 활용해 추가한다.

별도로 작성한 기록된 방문·경로 예제와 빈 입력 실패 결과도 제공한다. 이는 화면 상태 개발용이며 원시 관측점에서 경로를 추론하거나 실제 입력 형식의 지원을 확정한 것이 아니다.

## 파일 담당 범위

| 담당 | 주 수정 범위 | 경계 |
| --- | --- | --- |
| 데이터 처리 | `src/parser/`와 그 테스트 | 공통 계약을 반환. UI·지구본·사진 URL에 의존하지 않음 |
| 화면·통합 | `src/app/`, 향후 `src/features/`, `src/main.tsx` | 합성 결과로 먼저 개발, 파서 PR 병합 후 실제 파서 연결 |
| 공통 변경 조율 | `src/domain/`, `src/fixtures/`, 패키지·잠금·빌드 설정, PRD·README·spec | 한 담당자가 변경하고 양쪽이 같은 계약 버전을 사용 |

공통 기반 PR이 main에 병합된 뒤 두 작업이 같은 기준에서 출발한다. 데이터 처리 PR을 먼저 검토·병합하고 화면 작업에서 최신 main을 반영해 통합한다. 통합 수정은 화면 브랜치를 재사용한다. 각 작업의 의미 있는 수정마다 커밋·푸시하고 GitHub PR 검토·병합 후 관련 브랜치와 worktree를 정리한다. 별도 통합 브랜치를 기본으로 만들지 않는다.

## 실행과 검증

앱은 Node 22.12 이상을 요구하며 Node 24 환경에서 검증한다. 의존성 버전은 package-lock.json으로 고정한다. 샘플 도구는 계속 설치 없이 브라우저에서 실행할 수 있다.

- 앱 타입 검사, 합성 계약 테스트, 프로덕션 빌드
- 기존 샘플 도구 전체 회귀 테스트
- 브라우저에서 앱 준비 화면과 기존 샘플 도구 확인
- 실제 원본·생성 샘플·사진의 Git 제외와 빌드 결과 제외 확인

기본 앱은 준비 상태를 명시하며 실제 파일을 선택하는 버튼을 제공하지 않는다. public 디렉터리 자동 복사를 끄고, 개발 서버도 private/local-data와 JSON·사진·환경 파일을 직접 제공하지 않도록 제한한다. 개발 서버 통신은 로컬 코드 제공 용도이며 향후 실제 데이터를 서버 요청으로 보내는 기능은 허용하지 않는다.

## 분리 착수 전 남길 결정

- 위치 점 연결을 먼저 개발할지, 연결 허용 시간 간격과 표현
- 앱 파서의 초기 지원 형식·용량·부분 실패 정책 (샘플 도구의 정책을 자동 적용하지 않음)
- 표시 시간대와 지원 브라우저 범위

위 결정 전에도 공통 기반은 완성할 수 있다. 공통 기반 완료는 실제 JSON 호환성이나 MVP 완료를 뜻하지 않는다.
